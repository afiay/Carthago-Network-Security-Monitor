## Bounded source-only inspector contract

The caller attests **one complete plaintext TCP EtherNet/IP encapsulation message**, verified source/destination ports and direction. The inspector rejects absent attestation, UDP, wrong or ambiguous 44818 direction, <24 or >65535 bytes, mismatched 16-bit little-endian declared length, nonzero reserved options and nonzero status (conservative subset). It recognizes 0x0065 RegisterSession only with a four-byte version-1/options-zero body and direction-appropriate session handle; 0x0066 UnregisterSession only as a zero-body client request with nonzero handle. 0x006F SendRRData and 0x0070 SendUnitData require nonzero handle, zero interface handle, exactly two bounded CPF items with expected address/data types and at least two data bytes. The first CPF address is null for unconnected and four-byte connection address for connected; malformed lengths and extra bytes fail closed. This intentionally rejects many valid variants, errors, UDP discovery and extended CPF forms to prevent unsupported claims.

No sender context, session handle, CIP payload, object path, user, controller address or other sensitive byte is returned or retained. Observation fields are only command kind, total length, payload length and reply direction. The observer is stateless, deterministic, allocation-free for parsing, bounded by supplied span, and has no network, journal, UI, alert or sink side effects. It cannot prove a successful register/login, device configuration, malicious CIP command, exploit, safety outcome or authentication. CIP Security TLS/DTLS ciphertext **must not be supplied as plaintext**.

The ODVA [EtherNet/IP technical presentation](https://www.odva.org/wp-content/uploads/2022/06/2014_ODVA_Conference_Byres_Schweigert_Thomas_Securing_EtherNetIP_with_DPI_FINAL.pdf) describes the 24-byte little-endian encapsulation header; [ODVA technology overview](https://www.odva.org/publication_download/ethernet-ip-technology-overview/) distinguishes encapsulation from CIP services. [ODVA CIP Security](https://www.odva.org/technology-standards/distinct-cip-services/cip-security/) explains protected TLS/DTLS transport. The new code is independently authored from protocol structure, **not copied from Wireshark**.
