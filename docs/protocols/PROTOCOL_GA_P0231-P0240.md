The live fast path discards non-IP EtherTypes, accepts only Ethernet/loopback/Linux cooked link types, drops fragmented IPv4/non-first IPv6, and routes TCP/UDP/ICMP but not native PPP or CAN. Its TCP packet payload is **not** a reassembled application message. No verified ANCP, BFCP, ACN, PPP or CAN input adapter or authoritative service outcome was identified. A port/service label, dissector key, raw BFCP header, or vendor product name does not establish a trusted parser or exploit. The isolated BFCP inspector requires **three explicit caller attestations**: complete transport message/datagram, negotiated BFCP session, trusted plaintext source. Those booleans are *caller obligations*, not cryptographic verification performed by the inspector. TLS/DTLS ciphertext is **NOT OBSERVABLE** without an approved endpoint/proxy source. BFCP over UDP may be fragmented: only individual fragments are bounded and classified; no reassembly or transaction tracking occurs.

The BFCP inspector is stateless and allocation-free per call, caps input at 4096 bytes, checks version/transport compatibility, primitive range, reserved bits, 4-byte payload units, exact complete-frame length and fragment offset/length bounds before slicing. It exposes only version, primitive, response/fragment *unverified flags*, declared/observed byte counts; **conference ID, transaction ID, user ID, attributes and payload are not retained**. Rejecting nonzero reserved bits and reliable-transport R/F bits is intentionally stricter than RFC receiver interoperability rules to minimize false recognition. This is not an authoritative BFCP implementation, full attribute decoder or server outcome verifier. An attacker could still forge a structurally valid header: false positives are possible without trusted SDP and endpoint provenance.
