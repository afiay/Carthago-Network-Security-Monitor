| **P0411 `btavdtp` — Bluetooth AVDTP** | **BLOCKED — NATIVE BLUETOOTH INPUT** | Real audio/video distribution transport signaling above L2CAP, not an IP port. Unexpected stream-endpoint configuration or renegotiation could be worth investigation **only** with HCI/host-derived connection handle, PSM/channel, signal identifier, peer/device role, direction and validated endpoint state. Legitimate tethering and managed PAN are strong negatives. Ordinary Ethernet/IP packets do not prove Bluetooth carriage. [SIG specifications](https://www.bluetooth.com/specifications/specs/). |
| **P0413 `btgatt` — Bluetooth GATT** | **REJECTED_DUPLICATE_OR_NOT_A_PROTOCOL — PROFILE, NOT SEPARATE WIRE DECODER** | Generic Attribute Profile specifies service/characteristic behavior over **ATT** (P0410 `btatt`, already blocked). Do not count GATT as a second independent on-wire parser. Unauthorized characteristic writes would require ATT opcode, characteristic UUID/handle, authenticated peer, device policy and accepted server outcome from a trusted host/HCI adapter; benign configuration/firmware updates are common. Normal multi-channel negotiation and retransmission are benign. IP-only fast path cannot deliver these bytes. [Core L2CAP](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-62/out/en/host/logical-link-control-and-adaptation-protocol-specification.html). |

Normal link setup, role switch and rekeying are negatives. Neither Ethernet/IP nor ordinary Windows network ETW exposes the required controller PDUs. [Core specification](https://www.bluetooth.com/specifications/specs/core-specification-6-3/). |
| **P0416 `btmcap` — Bluetooth MCAP** | **BLOCKED — NATIVE BLUETOOTH INPUT** | Medical-device profile adaptation control; hypothetical unauthorized data-channel creation requires MCAP control messages, reliable L2CAP channel identity, device/profile policy, authenticated peer and host accepted-channel outcome. ## Live-source divergence and sensor boundary

- At source base `7a6152e013022dd72df396a62b8c6b63cab008b5`, [`PacketHandler.cs`](../../Carthago/Services/PacketHandler.cs) accepts Ethernet (DLT 1), loopback (0), raw IP (12/101/228/229), and Linux cooked (113/276); unrecognized link types return null, and all non-IPv4/IPv6 EtherTypes return null. Bluetooth HCI, ACL, L2CAP, controller and profile payloads therefore have **no demonstrated producer**. `TrafficCaptureService.cs` uses SharpPcap or ETW traffic records, not a Bluetooth host/controller adapter.
- Inspected [`TrafficRecord.cs`](../../Carthago/Models/TrafficRecord.cs) and selected OT, MQTT, SMB2, FTP, SNMP, Syslog, Windows Security and MsQuic ETW producers. None of these supplies trusted Bluetooth link handle, CID, authenticated pairing outcome or profile operation. [`PortServiceResolver.cs`](../../Carthago/Services/PortServiceResolver.cs) is service metadata, not Bluetooth decoding. Repository tree inspection found no protocol-stream-owned Bluetooth decoder or Bluetooth HCI capture bridge at the source SHA.
- Existing `R468_BluetoothGatewayInternetEgressRule` is a **detection descriptor/flow rule**, not evidence of native Bluetooth HCI/ATT/GATT payload ingestion. Do not change that rule or its ledger.
- The `Carthago.csproj` SDK auto-includes normal `.cs` files, but **no parser is authored** here: adding one without the native input would falsely imply usable capture coverage. Any future standalone parser must remain ISOLATED — NOT LIVE-CAPTURE INTEGRATED until owner-approved wiring and verified tests.

## Minimal future integration proposal — NOT authorized or implemented

**Separate coordination GA only, after explicit owner approval.** Add an opt-in, host-native Bluetooth telemetry adapter (or separately permissioned HCI capture source) that produces a narrow immutable `BluetoothEvidenceEnvelope` with trusted provider, device-instance/controller, link type, direction, monotonic capture timestamp, connection handle, channel/CID, protocol family, complete-frame status, security/authentication state **only if attested**, and bounded payload length. Never interpret an Ethernet frame, service name, DNS, IP flow or the existing R468 descriptor as Bluetooth provenance.

Consumers: isolated, protocol-owned bounded inspectors with strict L2CAP/ATT/AVDTP/RFCOMM/etc. frame lengths and complete-message requirements. No payload retention, personal device names, pairing keys, contact names, object contents or unrestricted MAC addresses in journal/UI. Require explicit user opt-in, bounded queues, TTL/fragment caps, redaction, out-of-order handling, disabled-by-default behavior and no direct alert emission. Shared capture and `TrafficRecord` changes are **coordination-required**, not part of this GA.

**Compatibility/test proposal (not authored or executed):** valid attested native message; IP/Bluetooth cross-protocol negative; malformed/truncated/oversize input; fragmented/reordered/replayed ACL/L2CAP with bounded state; encrypted/non-observable or absent provenance fail-closed; device disconnect/reconnect and concurrent sessions; legitimate audio/PAN/medical-device maintenance controls; opt-in off and rollback. Rollback removes the optional adapter/consumer and preserves existing capture, detection, journal and UI contracts. No runtime integration before source review and owner approval.
