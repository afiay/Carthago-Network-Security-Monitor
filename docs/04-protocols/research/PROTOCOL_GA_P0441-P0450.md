The inspector accepts a contiguous **8-byte-or-longer prefix only at an independently attested TCP connection start**. It validates network-order version **100** and advertised fixed-header length **56–4096 bytes**; the historical ISC protocol document specifies 56 as normal and permits larger headers. Input prefix is capped at **4096 bytes**, no allocations except the small value-type observation, no mutable state, I/O, timers, regex or sensitive strings. Larger extensions are **unsupported, not suspicious**. No body, operation, authentication signature, transaction ID, asset identity, endpoint configuration, successful action, or resource exhaustion is parsed or asserted. Fragmented/missing-prefix traffic is not classifiable without a separately approved trusted TCP reassembler. A malicious party can forge the 8-byte prefix; even a structurally correct result is **not** proof of OMAPI or compromise without trusted producer/asset evidence.

## Threat refresh — 2026-11-01

**P0441: VENDOR_ADVISORY_NO_EXPLOIT_EVIDENCE.** [ISC operational notification dated 2026-10-01](https://kb.isc.org/docs/isc-dhcp-omapi-interface-memory-usage-attack) names ISC DHCP **4.1-ESV-R1 through 4.1-ESV-R16-P1** and **4.4.0 through 4.4.3**, and advises that older OMAPI-capable releases may be affected. Prerequisite: unauthenticated attacker can connect to exposed OMAPI port; potential outcome: unbounded server memory usage and availability loss. It provides **no established wild-exploitation claim, CVE identifier, per-device IOC or validated signature**. [ISC OMAPI access guidance](https://kb.isc.org/docs/aa-01355) recommends firewall restrictions and shared keys. OMAPI's default TCP/7911 is configurable. Asset/version/config, exposure, connection telemetry and host memory metrics are the correct evidence path; the isolated prefix inspector is not a DoS detector.
