Ethernet/IP fast path drops non-IP frames and unrecognized L4, has no native CAN/PPP/UAV-radio input, drops IPv4 fragments and noninitial IPv6 fragments, and does not promise TCP message reassembly. UDP frames can reach the raw capture path but **there is no GVCP inspector invocation or trusted GVCP-specific record producer**. Port-service names are hints, not parsers. Existing Cisco SNMP is an active client and Cisco Syslog a separate listener; neither supplies PPP/CAN/CIP motion/GVCP configuration outcomes. Encrypted/private device channels remain **NOT OBSERVABLE** absent trusted endpoint/service evidence.

The GVCP inspector requires three explicit caller attestations: complete UDP datagram, independently verified GVCP control endpoint, and plaintext source. The flags are **not cryptographically verified** by the inspector. It accepts only 8–4096-byte datagrams with 0x42 request key, two known request flag shapes, big-endian command and payload length exactly matching the datagram, and conservative command-specific payload lengths. It rejects ACK-shaped responses, unsupported commands/flags, truncation, excess bytes, unknown framing and missing provenance. It is stateless, uses no heap allocation per call, no string parsing, no regex, no shared mutable state, no network or external side effects. Restricting recognized commands/flags may exclude valid vendor extensions; even a structurally valid request may be forged. It returns only command kind, broadcast flag, payload length and unverified potential-configuration-attempt flag; it deliberately discards request ID, device MAC/IP, register addresses/values and all payload bytes. No direct alert, event, UI, journal, external sink, raw DetectionEvent or confidence modification.
